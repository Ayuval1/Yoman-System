## 5. איך נשמר

**טבלה חדשה `intake_checks`** (מבנה לפי 46; `NOT NULL` ו-`DEFAULT` הם הצעה כמו ב-M.1) `[הצעה]`:

```sql
CREATE TABLE IF NOT EXISTS intake_checks (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  outcome_id uuid        NOT NULL REFERENCES intake_outcomes(id),
  verdict    text        NOT NULL,   -- right / wrong / was_event / not_event. בלי CHECK, כמו status ב-intake_outcomes
  event_type text,                   -- מלא רק כש-verdict = was_event: short_day / cancel / move / exam / homework / room (D14)
  checked_at timestamptz NOT NULL DEFAULT now()
);
```

- append-only (D5): אין `UPDATE` ואין `DELETE`. סימון חוזר הוא שורה נוספת, והאחרון (`checked_at`, ובשוויון `id`) קובע (D17.5). בלי טקסט ובלי שמות (D7).
- "סומן" = קיימת לפחות שורה אחת ל-`outcome_id`. אין אינדקס: מצופים מאות שורות לכל היותר `[הנחה]`. אם ייווצר אחד, זה `CREATE INDEX IF NOT EXISTS`, ויובל מריץ גם אותו.
- נכתבת בסשן בנייה לקובץ `db/schema.sql` (בתוך הקובץ, כי `test/schema.test.js` אוסר ALTER) ובמסד החי בידי יובל, בכרטיס פעולה (`vercel-fast-check/template/owner-action-card.md`). **Claude לא כותב למסד החי ולא מכבה את Read-only.** אחרי הכרטיס: צילום מסך של המתג לפני כל דבר אחר (`24`, "סשן 13.10").

**מה נחשב "לממתין לסימון" (SQL תיאורי, הבנייה קובעת את הצורה):** `intake_outcomes o` עם `sources s` (`channel = 'shortcut'`), `o.status <> 'duplicate'`, `s.received_at` ו-`o.recorded_at` בתוך `[REVIEW_FROM_DAY, REVIEW_LAST_BOUNDARY]`, `o.recorded_at <= B`, `o.recorded_at > B3` (T3); נציג אחד לקבוצת (`content_hash`, `(s.received_at AT TIME ZONE 'Asia/Jerusalem')::date`) (T4); בלי שורה ב-`intake_checks` (תנאי הרשימה בלבד; תנאי הכתיבה בלעדיו, T6).
**`B`:** 21:00 האחרון שחלף לפי `Asia/Jerusalem`, מחושב ב-JS עם `nextRunUtc` (`lib/schedule-time.js:54`) ומועבר כפרמטר, כך שאין חישוב תאריכים ב-SQL. בצרכן התור `B` נגזר מ-`targetAt`. `[הצעה]` חישוב: `nextRunUtc({from: now})` נותן את הגבול הבא; הקודם הוא `nextRunUtc({from: הבא − 26 שעות})`. הרציונל: מרחק של 23 עד 25 שעות בין גבולות (מעבר שעון), ו-26 שעות תמיד נופלת לפני הגבול הקודם.

## 6. החוזה

**`GET /api/chat`** מחזיר, בנוסף ל-`items`, `pending`, `badge`, מפתח `review`:

```
review: { total: N, items: [ { outcome_id, view: 'recorded'|'missed', text, result, missing, at } ] }
```
- `text`: ה-`raw_content` של המקור (הדף חותך ל-2 שורות). `at`: `received_at` ב-ISO.
- `result` (רק ב-`recorded`): מחרוזת בצורת `formatReply` בלי הקידומת "נרשם" (`lib/intake-questions.js:197`): "מבחן · מתמטיקה · שלישי 20.10". **התאריך: העובדה `new_date` בסוג `move`, ו-`date` בשאר** (כמו `replyFor`, `lib/intake-process.js:191`). `formatReply` זורק `RangeError` על סוג לא מוכר או תאריך לא תקין: הבונה תופס, ומציג מה שידוע בלי לזרוק. "חסר": לשדה מ-`ESSENTIAL_FIELDS` של הסוג (`lib/intake-facts.js:31`) שאין לו עובדה, **רק כשקיימת שאלה פתוחה** (`messages.kind='question'`, `awaiting_reply=true`) **למקור**; שם השדה החסר אינו שמור ב-`messages` (רק `body` חופשי), ולכן מציגים "חסר" כללי עם רשימת כל השדות החסרים, או משתמשים ב-`pendingQuestion` (`lib/intake-process.js:385`) לקבוע את השדה הבא; הבנייה בוחרת, והבחירה נרשמת. בלי שאלה פתוחה: שדה חסר לא מוצג. "לא ידוע" לעובדה בערך `unknown`. `missing`: שמות השדות (מקצוע, תאריך, תאריך חדש, נושא, חדר, שיעור) `[הצעה]`.
- סדר: `missed` קודם, אחר כך `recorded`, בכל חלק הוותיק קודם (D10). **בלי תקרה.** `total` = מספר ההודעות.
- כשאין הודעות לסימון: `review: { total: 0, items: [] }`.

**`POST /api/chat`** `{ action: 'check', outcome_id, verdict, event_type? }` → `{ status, review, badge }`. `review` בתשובה הוא הרשימה העדכנית של הממתינים (בלי מסומנים); שורות שסומנו בזמן שהרשימה פתוחה נשארות בדף כ"סומן: ... · שינוי" ונשמרות במצב הדף עד סגירה או רענון:
- `checked`: נכתבה שורה אחת (גם כשכבר יש סימון קודם: שינוי). `closed`: ה-outcome לא ניתן לסימון עכשיו (פקע, חדש מדי, כפילות, תצוגה אחרת מהמסד, קבוצה שנציגה אחר, או אינו קיים); לא נכתב דבר. הדף מתרענן.
- 400 (`לא נשלח, נסה שוב.` כמו היום): `outcome_id` לא uuid; `verdict` לא אחד מארבעה; `event_type` קיים כש-`verdict` אינו `was_event`, או חסר כש-`was_event`, או לא אחד מהשישה.
- הכתיבה: פקודת SQL אחת (`INSERT ... SELECT ... WHERE <תנאי החלון, הנציג והתצוגה התואמת לסימון; בלי התנאי "לא סומן"> RETURNING id`), שאין בה טקסט הודעה. אין `UPDATE` ואין `DELETE`.
- 401 / 405 / 500 כמו שאר הנקודה.

**התראה, במשבצת `close`:** `api/queues/deliver.js` קורא פונקציה חדשה ב-`lib/chat-notify.js` (שמשתמשת ב-`handle` של `push-send` כמו `sendChatNotification`): `title` = "מערכת יומן", `body` = "סיכום היום מחכה לסימון", `navigate` = '/', `app_badge` = המספר המלא (מוגבל ל-9999), `dedupe_key` = מפתח המשבצת. כשל בשליחה לא זורק ולא משנה את שורת `message-slot` (אותה התנהגות כמו `notify`). בלי תוכן הודעה בשום מקום (גבולות 46).

**עדכון 25.10.2026 (B-3א, `68` D11-D12, באישור יובל; שינוי כלל, לא הוספה):** ההתראה והפס נוצרים כשיש הודעות לסימון **או** שיש מבחן מחר. `sendReviewNotification` מקבלת `examLine` ("מחר: <סוג> ב<מקצוע> (ב-<שעה>, אם ידועה)", מחושבת ב-`lib/exam-line.js`, `examLineAt`, בחלון 21:00-06:00). רק מבחן: `body` = השורה. מבחן והודעות: `<שורה> · סיכום היום מחכה לסימון`. הודעות בלי מבחן: כמו למעלה. אף אחד: `review-zero` כמו קודם. `app_badge` והמספר על האייקון לא משתנים: שורת מבחן בלי הודעות אינה נספרת. חלון 14 הערבים של M.2 (`REVIEW_LAST_BOUNDARY`) אינו חל על שורת המבחן. שורת `probe_log` של `chat-notify` נושאת `exam=1` או `exam=0`.
